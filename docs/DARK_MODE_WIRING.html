Dark Mode Wiring (Quarto + Bootstrap)

Context

We currently implement dark mode via CSS variables in styles.css using @media (prefers-color-scheme: dark).

This works well for post pages, but the listing view (homepage listing) wraps titles and descriptions in <a> tags, which can pick up Bootstrap/Quarto link styling instead of our intended --black / --mid-gray tokens. Compounding this, the generated site is currently built with a single light Bootstrap theme (e.g. data-mode="light" and body.quarto-light), so some Bootstrap variables remain “light” even when the OS prefers dark.

The goal is to make listing titles + descriptions match the post view’s title/description styling in both light and dark modes, while preserving the existing visual identity and keeping the wiring clean (no bloat, no hacky CSS wars).

Goals

  • Consistency: Listing title/description typography + color match the post title banner’s title/description styling.
  • Correct modes: Both light and dark render correctly.
  • System preference: Site follows the OS/browser preference for dark mode (current behavior).
  • Minimal change surface: Adjust only the wiring + the minimum CSS needed for listing anchors to inherit properly.
  • Maintain visual identity: Keep the “industrial plotting paper” aesthetic; no Bootswatch “darkly” aesthetic takeover.

Non-goals

  • Redesigning the site or changing typography/layout.
  • Adding a custom theme switcher UI beyond what Quarto already provides.
  • Editing generated _site/ artifacts directly (they are build outputs).

One decision to confirm (before implementing)

Quarto’s official dark-mode support adds a theme toggle UI automatically when both light + dark themes are provided.

  • Option A (preferred for robustness): Allow the toggle to exist, but default behavior follows system preference.
    • Pros: Fully supported by Quarto; users can override if they want.
    • Cons: Not “system only” (users can override).
  • Option B (strict “system only”): Keep system-following behavior and remove the toggle from UX.
    • Pros: Preserves the “system only” product decision.
    • Cons: Quarto doesn’t document a supported “disable toggle” option; hiding it would likely require CSS (small and stable, but arguably “hacky”).

Action: Decide whether we accept the built-in Quarto toggle (A) or need strict system-only (B). The plan below supports both; implementation steps differ slightly.

Solution alternatives (high-level)

Alternative 1 — Quarto-native dual theme + respect-user-color-scheme (recommended)

Use Quarto’s supported dark mode wiring:

  • Provide both theme.light and theme.dark in _quarto.yml.
  • Set respect-user-color-scheme: true so initial render honors OS/browser preference.
  • Keep cosmo as the base theme for both, and add a small theme-dark.scss that overrides Bootstrap’s Sass variables to match the site’s dark palette.
  • Add minimal CSS for listing anchor wrappers so link text inherits the desired colors/weights.

This is the cleanest approach because it makes Bootstrap itself “dark-aware” instead of fighting light Bootstrap variables in dark mode.

Alternative 2 — Stay single-theme and override Bootstrap variables via prefers-color-scheme

Keep a single Bootstrap build, but override key --bs-* variables and/or link rules inside @media (prefers-color-scheme: dark) in styles.css.

  • Pros: No toggle is introduced.
  • Cons: More brittle: you’re essentially maintaining a parallel “dark bootstrap layer” and can miss variables used by Quarto components (listings, pagination, search UI, etc.).

Alternative 3 — Extension-based auto-dark

Use a Quarto extension (e.g. quarto-auto-dark) to retrofit automatic dark mode.

  • Pros: Potentially minimal YAML changes.
  • Cons: Adds a new dependency/pattern; less desirable given the “minimalist, non-bloated” constraint.

Proposed architecture (what we want after the change)

Layers

  1. Bootstrap theme (Quarto-compiled)
    • Defines Bootstrap variables for light and dark mode (body, links, UI components).
  2. Brand tokens (_brand.yml)
    • Keeps consistent typography + “brand-level” settings.
  3. Site custom CSS (styles.css)
    • Owns the unique aesthetic (dot grid, borders, layout, listing formatting) using our tokens (--paper, --black, etc.).

Data flow (build + runtime)

  A["Source config<br/>_quarto.yml"] --> B["Quarto render"]

  E["styles.css<br/>site aesthetic"] --> B

  G --> H["Listing view + Post view"]

What “correct” means (definition of done)

  • Listing title color/weight matches post title (visually).
  • Listing description color matches post description (visually).
  • Works in:
    • Light mode
    • Dark mode
  • Works on:
    • Homepage listing (index.qmd)
    • Any post page (posts/*/index.ipynb → generated HTML)

Implementation plan (phased, reviewable)

Phase 0 — Baseline + acceptance criteria (no code changes)

    • Listing view (light + dark)
    • One post page (light + dark)
    • Is the problem title color, description color, underline/decoration, font weight, or all?
    • Decision: Option A (toggle allowed, system preference honored by default)

Phase 1 — Wire Quarto for true dual-mode Bootstrap

Goal: Ensure Quarto can output both light + dark Bootstrap CSS and select based on system preference.

    • Provide both theme.light and theme.dark.
    • Enable respect-user-color-scheme: true.

Example wiring (to be adapted to this repo’s exact paths):

format:
  html:
    theme:
      light: [cosmo, _brand.yml]
      dark: [cosmo, _brand.yml, theme-dark.scss]
    respect-user-color-scheme: true
    css: styles.css
    • Keep this file minimal: only variables that matter for global readability and link colors.

Starter content (tokens must match styles.css dark palette):

/*-- scss:defaults --*/
// Base document colors
$body-bg: #1E1D1B;
$body-color: #E6E4DF;

// Links (listing wraps title/description in <a>)
$link-color: #E6E4DF;
$link-hover-color: #E6E4DF;

// Muted text used in some Bootstrap components
$text-muted: #B8B6B0;

// Optional: make borders match the “plotting paper” vibe
$border-color: #3D3B37;

/*-- scss:rules --*/
// Keep Quarto/Bootstrap from reintroducing underlines where we don’t want them.
// (Prefer handling listing-specific decoration in styles.css.)

Notes: - We intentionally keep this file “bootstrap-level” and leave layout/aesthetic to styles.css. - We should not fight bootstrap with !important here; use Sass variables first.

Phase 2 — Align custom tokens with Quarto’s active mode

This depends on the “toggle” decision:

Option A (toggle allowed)

Goal: Ensure our custom variables switch based on Quarto’s active mode (not only the OS media query), so the toggle doesn’t break our CSS.

    • @media (prefers-color-scheme: dark) { :root { ... } }
    • to a Quarto mode selector like:
      • body.quarto-dark { ... } (or html[data-bs-theme="dark"] { ... } depending on Quarto output)

This makes our CSS consistent with Quarto’s theme switching logic and prevents “OS says dark but user toggled light” mismatches.

Option B (strict system-only)

Goal: Preserve current prefers-color-scheme behavior.

    • Accept it anyway (fallback to Option A), or
    • Hide it with a minimal, well-targeted CSS rule (only if acceptable).

Phase 3 — Fix listing title/description anchor inheritance

Goal: Listing titles + descriptions are links, but should look like the post title/description.

Recommended minimal additions (exact selectors may be adjusted after inspection):

.quarto-post .listing-description a {
  color: inherit;
  text-decoration: none;
}

.quarto-post .listing-description a:hover {
  text-decoration: underline;
  text-underline-offset: 2px;
}

Also verify: - .quarto-post .listing-title a already uses color: inherit; text-decoration: none; - The delink wrapper class doesn’t introduce conflicting rules.

Phase 4 — Manual verification checklist (tight feedback loop)

    • Listing view title + description match post view title + description in light mode
    • Listing view title + description match post view title + description in dark mode
    • Title hover underline appears (if desired)
    • Description hover underline appears (if desired) and doesn’t look noisy
    • Navbar links
    • Sidebar category filter styling
    • Footer links
    • Code blocks + syntax highlighting (light/dark already configured in _quarto.yml)

Phase 5 — Documentation tidy-up

Files to change (expected)

  • /_quarto.yml
    • Add respect-user-color-scheme: true
    • Change theme: to light/dark mapping
  • /theme-dark.scss or /docs/theme-dark.scss (choose location; prefer project root for theme assets)
  • /styles.css
    • Adjust listing anchor inheritance
    • (Option A) change how dark tokens are activated (Quarto mode vs media query)
  • /docs/STRUCTURE.md
    • Document new file(s)

Risk / trade-offs

  • Toggle UX: Quarto’s supported dark mode comes with a toggle. If we must be strict system-only, we’ll need an explicit decision on whether hiding it via CSS is acceptable.
  • JS requirement: Quarto’s respect-user-color-scheme requires JavaScript (Quarto 1.7+). With JS disabled, the “first theme listed” is used.
  • Token duplication: If both theme-dark.scss and styles.css define colors, ensure they are consistent (avoid drifting palettes).

Rollback plan

  • Revert _quarto.yml to single-theme config.
  • Remove theme-dark.scss.
  • Revert any mode-switching selector changes in styles.css.
